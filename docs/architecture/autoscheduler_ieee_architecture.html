How to explain the figure

Read it from left to right. The upper half creates trustworthy evidence and selects a model. The lower runtime path uses that frozen model to recommend a scheduler, while hard rules retain final control.

1

Inputs and orchestration

Technical: the CLI fixes commands, seeds, paths, and configuration while workloads come from seeded generation or Linux traces. Analogy: this is the test organizer collecting exam questions and setting the rules.

2

Data preparation

Technical: traces become replayable process histories and observed-only feature rows, then complete traces are split without leakage. Analogy: the system writes study notes using only facts known at that moment.

3

Model selection

Technical: legal scheduling actions receive replay-based cost labels; five model families and two tree formulations are compared on common validation evidence. Analogy: several advisers answer the same practice tests, and the most useful one is sealed for the final demonstration.

4

Guarded runtime routing

Technical: Dynamic V3 reviews observed state every 10 ticks, but confidence, dwell, margin, and safe-boundary checks decide whether a policy switch is allowed. Analogy: the adviser recommends a driver, but a safety officer decides whether changing drivers is safe.

5

Execution and evidence

Technical: every policy shares one event engine and one metric implementation, producing comparable scores, fairness measures, latency, decisions, and a Gantt timeline. Analogy: every driver uses the same track and stopwatch, so the race is fair.

R

Research boundary

The simulator and offline replay provide controlled evidence, not proof of real kernel speed. Final deployment claims require the separate real-trace and sched_ext validation path.
